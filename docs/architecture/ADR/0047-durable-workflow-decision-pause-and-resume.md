# ADR-0047: Durable workflow decision pause and resume

- Status: Accepted
- Date: 2026-09-26
- Context: DecisionRequest and Decision contracts and atomic task-state decision submission exist, but a stage handler cannot pause a running task in a durable, scheduler-owned way. The run supervisor treats every execution return as terminal, and a selected decision is not replayed into the resumed stage invocation. A UI built on the current storage primitive could therefore record a choice without continuing the scientific stage safely.
- Decision: Add a typed DecisionRequired signal for stage handlers. The scheduler atomically records the offered DecisionRequest as a validation issue and transitions the task RUNNING -> AWAITING_DECISION, closes the current attempt with an awaiting-decision status, and yields a distinct awaiting_decision workflow outcome. The local queue persists that run status without marking the run finished. Decision submission must match the persisted issue and task version, record the decision and AWAITING_DECISION -> READY event atomically, and requeue the same run. When the scheduler replays the stage, the handler receives all prior task decisions in TaskInvocation and remains responsible for honoring them. Pending decisions are visible only after the run submission lease has entered awaiting_decision, avoiding the pause/submit race.
- Data: Reuse ValidationIssueRow for the request and DecisionRow.issue_id for the selected answer; no new schema table is needed. Add only enum/contract fields if compatibility requires them.
- Consequences: Existing successful outputs remain cacheable, task identity stays stable, the paused stage is retried from its handler boundary with explicit decisions, and prior successful stages are not recomputed. Arbitrary external processes are not assumed to be resumable; existing handler recovery remains authoritative. Each decision is task scoped initially; broader run/project scopes are retained as recorded metadata but do not imply automatic propagation.
- Alternatives considered: Frontend-only prompts (not durable); treating decision as failure (would trigger retry/failure policies); storing choices only in workflow JSON (loses who/when/rationale and cannot atomically resolve the waiting task); blindly resuming without passing the decision to the handler (scientifically unsafe).
